# 운영·데이터·안전 설계

## 데이터 수명과 보존

`news-state` 브랜치에서 `state.json`을 읽어 지난 실행 상태를 복구합니다. 같은 KST 날짜의 `days[date].articles`에 결과를 합치고 해당 날짜의 HTML을 다시 생성합니다. 일정별 결과는 `slots`, 수동 실행은 `manual_runs`에 분리해 기록합니다.

`seen`은 같은 URL과 정규화된 동일 제목의 중복 처리를 억제합니다. `news_candidates`와 `cve_candidates`에는 당일 재평가를 위한 짧은 후보 근거와 기존 요약을 보존합니다. Gemini 3.8 Flash가 의미 중복과 중요도를 판단해 뉴스 각 분야와 대표 CVE를 하루 최대 20건씩 선정합니다. 오후의 중요한 새 후보가 오전 선정을 대체할 수 있습니다. 선정되지 않은 후보는 요약 보류 건수에 포함하지 않습니다.

사회적 파급력·화제성·이슈성은 같은 비중으로 평가하도록 요청하며 실제 근거가 없는 조회수·유행·공격 사례를 만들지 않게 합니다. CVE는 같은 제품의 같은 문제에 한해 대표로 묶도록 요청합니다. 제품이 같아도 독립적인 취약점은 별도로 남을 수 있습니다. 관련 ID·NVD 링크·원래 CVSS는 보존하고 Gemini의 0~5 중요도 점수와 구분합니다. 이 정책 도입 전 과거 보고서는 기존 기록으로 표시하며 대량 재번역하지 않습니다.

`pending`은 요약하지 못한 수집 항목을 보관합니다. 충분한 근거가 없거나 호출 상한에 도달한 경우, 또는 API가 실패한 경우 다음 실행에서 다시 시도합니다. 뉴스의 발행 범위는 KST 어제 00:00~실제 수집 시각이며 누적 후보·기존 카드·보류 목록을 매번 다시 검사합니다. 전날의 유효 후보와 요약도 재사용하므로 `seen`에 있다는 이유만으로 어제 기사를 오늘 후보에서 잃지 않습니다. 날짜 미제공 자료는 수집 시각을 발행 시각으로 위장하지 않습니다. Atom `updated`만 있으면 발행일로 사용하지 않으며 원문 `datePublished`가 수정 시각보다 우선합니다.

‘최신’은 `latest_articles`에 독립 저장합니다. 논문·CVE·GitHub 관측값·시각 미상은 제외하고 실제 발행일순 첫 20건을 Gemini로 관련성·모집 마감·의미 중복 검증합니다. 의미 중복의 대표는 최신 발행 기사여야 하며, 입력 밖 ID나 잘못된 중복 관계는 거부합니다. 기본 최대 2회 요청, 8,192 출력 토큰과 낮은 추론 수준을 사용합니다. 빈 후보는 API를 호출하지 않습니다. 실패하면 이전 유효 목록과 `stale`을 표시하거나 `unavailable`을 표시합니다.

발행일 미상 HTML 목록은 선별 전에 최대 20건의 허용된 본문 메타를 확인합니다. 실패·시각 미제공 결과는 6시간 쿨타임 뒤 다시 확인하며 확보한 본문은 같은 실행의 요약에 재사용합니다. 본문 전체를 상태에 저장하지 않습니다. 분야 선정과 최신 선정의 ID 합집합만 요약하며, 최신 단독 기사 때문에 분야별 20건 상한이나 HOT 후보 수를 늘리지 않습니다. 화면과 `reports.json`의 총 이슈 수는 ID 합집합이며 `section_count`·`latest_count`·`counts`가 별도로 제공됩니다. 과거 보고서 재생성은 해당 보고서의 수집 시각으로 최신 범위를 계산합니다.

`repo_cache`는 동일 저장소 설명의 중복 번역 요청을 줄입니다. 저장소의 `stars today`는 새 관측값으로 갱신하고 관측 시각을 표시합니다. 당일 일찍 수집된 뒤 최신 Trending 목록에서 빠진 저장소는 해당 날짜 보고서에 남을 수 있으므로 각 카드의 관측 시각도 함께 봐야 합니다. 이 순위는 오늘 보고서에 포함된 관측값의 정렬이지 GitHub 전체 전수 순위가 아닙니다.

## 5일 보관의 정확한 의미

한국시간 오늘을 포함한 5개 달력 날짜만 유지합니다. 매번 생성할 때 날짜 범위를 벗어난 상태를 제거하고 기존 `public/reports/`를 다시 만듭니다. 최신 사이트에서는 오래된 직접 주소도 더 이상 제공하지 않게 됩니다.

자정에 별도 삭제 작업을 돌리지는 않습니다. 실제 서버 파일 제거는 다음 성공한 배포 때 이루어집니다. 브라우저에서는 만료된 목록·보고서를 숨기는 보조 처리가 있지만 서버 삭제를 대신하지는 않습니다.

Git 커밋 이력, 옛 Pages 아티팩트, 외부 백업까지 영구 삭제하지 않습니다. `news-state`의 지난 커밋에는 이전 요약이나 짧은 RSS 제공문이 남을 수 있습니다. 보안 삭제가 필요한 용도라면 Git 이력이 아닌 별도 만료 스토리지와 접근 제어 설계가 필요합니다.

## 수집·요약 실패

| 상황 | 처리 |
|---|---|
| 일부 수집원 오류 | 다른 수집원은 계속 처리, 실패 사유를 상태 목록에 표시 |
| robots 제한·유료벽·CAPTCHA | 우회하지 않음. 충분한 RSS 제공문이 있으면 해당 범위로 요약 |
| 본문·설명 근거 부족 | 제목만 보고 내용을 만들지 않고 보류 |
| 요약 API 오류 | 이미 저장한 결과는 보존, 미완료 항목은 보류 |
| HOT API 오류 | 이전 HOT이 있으면 선정 시각과 함께 `stale` 표시. 없으면 선정 미완료 |
| 중복되지 않은 HOT 후보 부족 | 실제 가능한 개수와 부족 사유 표시. 가짜 항목으로 채우지 않음 |
| 상태 JSON 손상 | 빈 상태로 덮어쓰지 않고 오류로 중단 |
| news-state 원격 조회 실패 | 새 저장소처럼 취급하지 않고 중단 |
| 상태 push 충돌 | 강제 푸시하지 않음. 기존 배포 유지, 오류를 확인 후 재실행 |
| 실행 시간 초과·강제 취소 | 마지막 원격 저장·배포 이후 진행분은 남지 않을 수 있음 |

YAML의 `cancel-in-progress: false`는 기존 실행을 새 요청 때문에 취소하지 않도록 구성합니다. 이것이 예약의 정확한 실행 시각이나 실행 횟수를 보증하지는 않습니다.

## 예약 실행과 게시

GitHub 기본 예약은 `timezone: Asia/Seoul`과 KST cron으로 05:07·12:07·18:07에 준비하도록 지정합니다. 06:00·13:00·19:00까지 같은 `publish` runner에서 기다리고 Pages를 배포합니다. 수집 step 제한은 35분, 전체 작업 제한은 90분입니다. 2026년 10월 1일 조사에서는 06시 준비가 08:35에 생성됐고 전날 13시 준비도 18:31에 생성됐습니다. GitHub 기본 cron의 이벤트 생성 지연은 시간대 설정으로 제거할 수 없습니다.

상시 PC가 없는 경우 `scheduler/`의 Cloudflare Cron Worker가 독립적으로 `workflow_dispatch`를 호출합니다. Worker의 UTC cron은 KST 05:07·12:07·18:07에 대응합니다. `scheduledTime`에서 목표 날짜를 계산해 `publish_at`에 넣으므로 실제 처리 시각이 늦어져도 다음 날짜 슬롯으로 바뀌지 않습니다. 계정·비밀 키·트리거 등록은 별도 운영 설정이며, 등록 전에는 외부 예약이 활성화되지 않습니다. 외부 예약이 검증되면 `EXTERNAL_SCHEDULER_ENABLED=true`로 GitHub 기본 예약을 건너뜁니다. 설정 절차는 `scheduler/README.md`에 있습니다.

수집 기준 시각은 선행 작업의 실제 실행 시각입니다. 배포 작업은 목표 시각 이후 시작하더라도 GitHub Actions 대기열과 Pages 전파 시간 때문에 사이트 반영은 늦어질 수 있습니다.

게시 목표의 날짜는 작업 시작 때 한 번 계산합니다. 외부 예약이 `publish_at`을 전달하면 그 날짜를 사용하고, 없으면 Actions 실행의 원래 `created_at`을 사용합니다. GitHub 예약은 cron의 선언된 시간대에 따라 최근 준비 시각과 대응하는 슬롯을 계산합니다. 과거 UTC cron도 별도 매핑으로 지원합니다. 자정을 넘겨 실행되거나 재시도돼도 목표를 다음 날로 바꾸지 않고, 이미 지난 목표라면 즉시 배포합니다. 외부 호출은 목표보다 1시간 넘게 일찍 요청하면 오류로 중단합니다. 일반 수동 실행은 게시 대기를 생략합니다.

갱신 슬롯도 이 공개 목표 날짜에 기록합니다. 실제 수집 날짜에 생성한 뉴스와 NVD 공개 날짜별 CVE는 그대로 보존하며, 전날 저녁 작업이 오늘 새벽에 실행됐다고 오늘 저녁 완료로 표시하지 않습니다. 기존 상태에서 날짜를 잘못 기록한 슬롯은 저장된 처리 시각을 이용해 이전 날짜로 옮깁니다.

수집과 상태 저장이 성공했지만 배포가 실패했다면 Actions에서 `mode: rebuild`, `scheduled_slot: manual`로 실행해 저장된 요약을 다시 게시할 수 있습니다. 이 경로는 뉴스 수집이나 Gemini 호출을 추가로 수행하지 않습니다.
## API 사용량

선별은 후보를 최대 200건씩 나눠 Gemini가 평가하고 대표 후보를 다시 비교하는 방식입니다. 모든 후보가 평가 대상에 포함됩니다. 원본 응답 전체의 ID·의미 중복 관계·점수·한국어 이유와 형식을 검증한 뒤 논문→신기술, 행사→행사, Trending 저장소→GitHub 고정 분류를 코드에서 적용합니다. 분야별 20건 상한은 모델이 반환한 중요도 순서를 유지해 적용하며 Python이 점수나 CVSS로 다시 순위를 매기지 않습니다. 상한 때문에 제외한 기사를 같은 사건의 중복 기사로 기록하지 않습니다. 고정 분류를 모델이 어기는 것은 배치 중단 사유가 아닙니다.

입력에 없는 ID, 중복 대표, 잘못된 중복 관계·점수·한국어 이유 등은 전체 응답을 거부합니다. 상한으로 잘라낼 위치의 항목도 먼저 검증해 오류를 숨기지 않습니다. 일반 뉴스의 분류 등 남은 의미 검증 오류는 실패 종류에 맞는 고정 보정 지시를 추가해 기존 최대 2회 요청 안에서 재시도합니다. 실패 응답이나 API 키를 지시에 넣지 않습니다. 중간 결과를 최종 선정으로 게시하지 않으며, 끝내 선별에 실패하면 당일 이전의 유효한 결과를 유지하고 `stale`과 경고를 표시합니다. 당일 결과가 없으면 후보를 보존하고 게시를 중단합니다.

요청 응답 스키마의 뉴스 `category`는 `ai/security/tech` 세 주제만 허용합니다. 행사나 저장소를 일반 뉴스에 붙일 수 있는 이전의 5개 값 스키마를 좁혔습니다. `fixed_category`는 소스 종류에 따른 최종 보고서 분야이며 출력 주제와 별개입니다. 모델은 모든 후보의 주제를 세 값 중 하나로 반환하고 코드가 논문·행사·저장소의 실제 분야를 복원합니다. 20건 상한과 최종 검증은 복원한 5개 보고서 분야에 각각 적용합니다. 보정 지시만으로 불일치를 해결할 때의 반복 실패 가능성을 줄이며 요청 수를 늘리지 않습니다.

Actions의 `Process completed with exit code 1`은 여러 실패에 공통인 종료 표시입니다. 수집 단계의 앞선 구체적인 오류와 경고를 확인해야 합니다. 2026년 10월 9일에는 모델 분류와 기사 종류의 불일치가 네 시도에서 반복됐습니다. 전날 저녁에는 같은 오류가 있어도 기존 당일 결과를 유지해 배포가 성공했지만, 다음 날에는 유지할 결과가 없어 중단됐습니다. 예약 실행 자체와 새 선별 결과의 성공 여부는 별도로 확인해야 합니다.

실제 API가 큰 배열과 중첩된 숫자 범위 제약을 함께 넣은 선별 스키마에 HTTP 400을 반환해, 요청 스키마는 타입·필수 필드·카테고리 중심으로 단순화했습니다. 20건 상한과 0~5 점수, ID·중복 검증은 Python에서 그대로 강제합니다. `check-api`는 작은 가상 후보로 실제 뉴스·CVE 선별 스키마까지 확인하며 배포 권한·Pages 환경이 없는 별도 작업에서 실행됩니다. 유효한 이전 선정 없이 뉴스 선별이 실패하면 후보를 보존하고 게시를 중단합니다.

선정 기사만 본문을 확보하고 기본 6개씩 요약합니다. 선정 CVE만 번역하고 이전 날짜의 미번역 후보 전체를 자동 대기열에 넣지 않습니다. HOT은 최종 선정 기사 최대 100건에서 고르며 80건을 넘으면 분할 평가합니다. HOT 모델이 429·5xx를 반환하면 다른 설정 Gemini 모델을 시도하며, 401 인증 실패는 배포를 중단합니다. 선별·요약·HOT·CVE와 모든 재시도가 공통 호출 상한과 쿨타임을 사용합니다.

HOT 호출 예산은 이미 요약한 기사와 남은 호출 횟수로 이번 실행에서 요약 가능한 기사 수를 기준으로 예약합니다. 아직 요약하지 않은 전체 보류 목록을 HOT 후보로 계산하지 않습니다. 보류 항목이 많아져도 뉴스 처리 예산을 모두 HOT에 예약하는 순환을 방지하며, 실행당 80회 상한과 요청 간격은 유지합니다.

기본 80회 제한, 요청 시작 간 최소 10초, 429 뒤 30~60초와 짧은 무작위 지연, 기사당 입력 최대 6,000자를 사용합니다. 429 대기는 HOT 대체 모델과 CVE 요청에도 적용됩니다. 일일 호출량이나 토큰 한도를 넘겼다면 대기만으로 해결되지 않습니다. 충분한 근거가 원문 전체보다 짧은 경우 카드에 RSS·초록 기반임을 표시합니다. 본문 일부만 사용하므로 기사 끝부분의 예외 조건이나 맥락을 놓칠 수 있습니다. 중요한 판단은 반드시 원문으로 확인하세요.

요약/분류와 HOT은 하나의 Gemini 제공자를 사용합니다. 별도 출처 교차 검증이나 사람의 사실 검수가 이루어지는 것은 아닙니다. 모델의 환각·오역 가능성은 남습니다.

## 키·입출력 보안

API 키는 환경변수에서 읽고 Google API 인증 헤더에만 넣습니다. 클라이언트 JS, 페이지 JSON, Git 상태에는 넣지 않습니다. 수집용 HTTP 세션에는 API 키를 전달하지 않습니다. 전체 인증 헤더나 모델 원시 응답을 로그로 출력하지 않습니다.

기사 본문 속 명령을 따르지 않도록 시스템 지시와 외부 데이터 영역을 분리합니다. 모델에는 외부 도구를 제공하지 않습니다. 결과 JSON 스키마와 기사 ID, 길이, 한국어 요약을 검증하고 Jinja HTML 자동 이스케이프를 사용합니다. 모델이 HTML이나 JavaScript를 반환하더라도 코드로 실행하지 않습니다.

수집은 설정한 도메인과 그 하위 도메인으로 한정합니다. 요청·리디렉션 전 공개 IP 여부를 확인하고, 응답 크기·시간·요청 간격을 제한합니다. 이 검사가 모든 네트워크 공격이나 DNS 재바인딩을 완전히 막는다는 보증은 아닙니다. 공개 출처만 사용하고 Actions 권한을 최소화하는 것이 전제입니다.

`store:false`는 Interactions 상태 보관을 사용하지 않도록 요청하는 설정입니다. 모든 서비스 로그·과금 기록·제공자 데이터 정책을 통제한다는 의미는 아닙니다.

## 콘텐츠와 공개 범위

로그인하지 않은 공개 RSS·기사 일부·초록·저장소 설명을 수집 대상으로 삼습니다. 자동 접근이 가능하다는 사실만으로 모든 재게시 권리를 가진다고 판단해서는 안 됩니다. 운영 전 출처의 이용 조건을 확인하고, 요청이 있으면 해당 수집원을 제외하세요.

독자에게 제공하는 것은 짧은 한국어 요약과 원문 링크입니다. 기사 이미지, PDF 본문, 전체 HTML을 다시 게시하지 않습니다. 공개 저장소에서는 `news-state`의 요약·URL·보류 제공문도 공개이므로 기밀 자료를 넣지 마세요.
