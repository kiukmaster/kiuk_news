# 운영·데이터·안전 설계

## 데이터 수명과 보존

`news-state` 브랜치에서 `state.json`을 읽어 지난 실행 상태를 복구합니다. 같은 KST 날짜의 `days[date].articles`에 결과를 합치고 해당 날짜의 HTML을 다시 생성합니다. 일정별 결과는 `slots`, 수동 실행은 `manual_runs`에 분리해 기록합니다.

`seen`은 같은 URL과 정규화된 동일 제목의 중복 처리를 억제합니다. 모든 사건을 의미 단위로 완벽히 병합하는 전면 중복 제거는 아닙니다. 서로 다른 제목의 같은 사건은 분야별 카드에 남을 수 있고, HOT에는 같은 사건을 중복 선정하지 않도록 Gemini에 지시합니다.

`pending`은 요약하지 못한 수집 항목을 보관합니다. 충분한 근거가 없거나 호출 상한에 도달한 경우, 또는 API가 실패한 경우 다음 실행에서 다시 시도합니다. 기본 48시간 발행 범위를 넘긴 기사는 재시도 목록에서 빠집니다. 날짜 미제공 자료는 수집 시각을 발행 시각으로 위장하지 않습니다.

`repo_cache`는 동일 저장소 설명의 중복 번역 요청을 줄입니다. 저장소의 `stars today`는 새 관측값으로 갱신하고 관측 시각을 표시합니다. 당일 일찍 수집된 뒤 최신 Trending 목록에서 빠진 저장소는 해당 날짜 보고서에 남을 수 있으므로 각 카드의 관측 시각도 함께 봐야 합니다. 이 순위는 오늘 보고서에 포함된 관측값의 정렬이지 GitHub 전체 전수 순위가 아닙니다.

## 5일 보관의 정확한 의미

한국시간 오늘을 포함한 5개 달력 날짜만 유지합니다. 매번 생성할 때 날짜 범위를 벗어난 상태를 제거하고 기존 `public/reports/`를 다시 만듭니다. 최신 사이트에서는 오래된 직접 주소도 더 이상 제공하지 않게 됩니다.

자정에 별도 삭제 작업을 돌리지는 않습니다. 실제 서버 파일 제거는 다음 성공한 배포 때 이루어집니다. 브라우저에서는 만료된 목록·보고서를 숨기는 보조 처리가 있지만 서버 삭제를 대신하지는 않습니다.

Git 커밋 이력, 옛 Pages 아티팩트, 외부 백업까지 영구 삭제하지 않습니다. `news-state`의 지난 커밋에는 이전 요약이나 짧은 RSS 제공문이 남을 수 있습니다. 보안 삭제가 필요한 용도라면 Git 이력이 아닌 별도 만료 스토리지와 접근 제어 설계가 필요합니다.

## 수집·요약 실패

| 상황 | 처리 |
|---|---|
| 일부 수집원 오류 | 다른 수집원은 계속 처리, 실패 사유를 상태 목록에 표시 |
| robots 제한·유료벽·CAPTCHA | 우회하지 않음. 충분한 RSS 제공문이 있으면 해당 범위로 요약 |
| 본문·설명 근거 부족 | 제목만 보고 내용을 만들지 않고 보류 |
| 요약 API 오류 | 이미 저장한 결과는 보존, 미완료 항목은 보류 |
| HOT API 오류 | 이전 HOT이 있으면 선정 시각과 함께 `stale` 표시. 없으면 선정 미완료 |
| 중복되지 않은 HOT 후보 부족 | 실제 가능한 개수와 부족 사유 표시. 가짜 항목으로 채우지 않음 |
| 상태 JSON 손상 | 빈 상태로 덮어쓰지 않고 오류로 중단 |
| news-state 원격 조회 실패 | 새 저장소처럼 취급하지 않고 중단 |
| 상태 push 충돌 | 강제 푸시하지 않음. 기존 배포 유지, 오류를 확인 후 재실행 |
| 실행 시간 초과·강제 취소 | 마지막 원격 저장·배포 이후 진행분은 남지 않을 수 있음 |

YAML의 `cancel-in-progress: false`는 기존 실행을 새 요청 때문에 취소하지 않도록 구성합니다. 이것이 예약의 정확한 실행 시각이나 실행 횟수를 보증하지는 않습니다.

## 예약 실행과 게시

GitHub 기본 예약은 05:07·12:07·18:07 KST에 수집을 시작하고 목표 시각 06:00·13:00·19:00 KST까지 배포를 대기합니다. 공개 저장소의 최근 예약 8건은 작업 생성 자체가 예정 시각보다 2시간 14분~4시간 55분 늦었으므로, 비정각 선행 예약만으로 정시성을 보장하지 않습니다. 외부 HTTPS 예약 서비스에서 `workflow_dispatch`의 `scheduled_slot`을 전달하는 방법은 `SETUP.md` 10절에 있습니다. 외부 서비스가 검증되면 `EXTERNAL_SCHEDULER_ENABLED=true`로 GitHub 기본 예약을 건너뛰어 중복 실행을 피할 수 있습니다.

수집 기준 시각은 선행 작업의 실제 실행 시각입니다. 배포 작업은 목표 시각 이후 시작하더라도 GitHub Actions 대기열과 Pages 전파 시간 때문에 사이트 반영은 늦어질 수 있습니다.
## API 사용량

요약은 기본 6개씩 묶습니다. HOT 후보가 80건을 넘으면 Gemini가 그룹별로 10건씩 예선 선정하고 남은 후보에서 최종 10건을 고릅니다. HOT 모델이 429·5xx를 반환하면 다른 설정 Gemini 모델을 시도하며, 401 인증 실패는 배포를 중단합니다. 새 기사 수뿐 아니라 후보 전체 길이도 HOT 입력 토큰에 영향을 줍니다. 429·5xx·일부 JSON 검증 실패에는 제한된 재시도를 수행하며 재시도도 요청 상한에 포함합니다.

기본 80회 제한, 요청 시작 간 최소 10초, 429 뒤 30~60초와 짧은 무작위 지연, 기사당 입력 최대 6,000자를 사용합니다. 429 대기는 HOT 대체 모델과 CVE 요청에도 적용됩니다. 일일 호출량이나 토큰 한도를 넘겼다면 대기만으로 해결되지 않습니다. 충분한 근거가 원문 전체보다 짧은 경우 카드에 RSS·초록 기반임을 표시합니다. 본문 일부만 사용하므로 기사 끝부분의 예외 조건이나 맥락을 놓칠 수 있습니다. 중요한 판단은 반드시 원문으로 확인하세요.

요약/분류와 HOT은 하나의 Gemini 제공자를 사용합니다. 별도 출처 교차 검증이나 사람의 사실 검수가 이루어지는 것은 아닙니다. 모델의 환각·오역 가능성은 남습니다.

## 키·입출력 보안

API 키는 환경변수에서 읽고 Google API 인증 헤더에만 넣습니다. 클라이언트 JS, 페이지 JSON, Git 상태에는 넣지 않습니다. 수집용 HTTP 세션에는 API 키를 전달하지 않습니다. 전체 인증 헤더나 모델 원시 응답을 로그로 출력하지 않습니다.

기사 본문 속 명령을 따르지 않도록 시스템 지시와 외부 데이터 영역을 분리합니다. 모델에는 외부 도구를 제공하지 않습니다. 결과 JSON 스키마와 기사 ID, 길이, 한국어 요약을 검증하고 Jinja HTML 자동 이스케이프를 사용합니다. 모델이 HTML이나 JavaScript를 반환하더라도 코드로 실행하지 않습니다.

수집은 설정한 도메인과 그 하위 도메인으로 한정합니다. 요청·리디렉션 전 공개 IP 여부를 확인하고, 응답 크기·시간·요청 간격을 제한합니다. 이 검사가 모든 네트워크 공격이나 DNS 재바인딩을 완전히 막는다는 보증은 아닙니다. 공개 출처만 사용하고 Actions 권한을 최소화하는 것이 전제입니다.

`store:false`는 Interactions 상태 보관을 사용하지 않도록 요청하는 설정입니다. 모든 서비스 로그·과금 기록·제공자 데이터 정책을 통제한다는 의미는 아닙니다.

## 콘텐츠와 공개 범위

로그인하지 않은 공개 RSS·기사 일부·초록·저장소 설명을 수집 대상으로 삼습니다. 자동 접근이 가능하다는 사실만으로 모든 재게시 권리를 가진다고 판단해서는 안 됩니다. 운영 전 출처의 이용 조건을 확인하고, 요청이 있으면 해당 수집원을 제외하세요.

독자에게 제공하는 것은 짧은 한국어 요약과 원문 링크입니다. 기사 이미지, PDF 본문, 전체 HTML을 다시 게시하지 않습니다. 공개 저장소에서는 `news-state`의 요약·URL·보류 제공문도 공개이므로 기밀 자료를 넣지 마세요.
